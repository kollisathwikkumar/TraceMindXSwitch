This document is the current-state source of truth. The longer workspace-root architecture proposal is a design reference, not an as-built specification. Status labels mean:

- **Implemented** — code and focused tests exist for the described bounded behavior.
- **Partial** — a useful, tested slice exists, but coverage, integration, or workflow is incomplete.
- **Unavailable** — the current user-facing path is blocked on this host/capability, or is not implemented.
- **Future** — design target only; no present product behavior is implied.

## Current product slice

TraceMind currently adds local project audits, a persisted static evidence graph, a persisted issue lifecycle and timeline, revision-aware report previews, and reviewable fixed check proposals to the Switch desktop app. The investigation report is a useful but partial dossier, not an exhaustive verification record. The graph records extracted leads; it does not establish semantic truth, causal explanation, or test coverage.

## Components and persisted records

- The renderer is `src/renderer/features/tracemind/tracemind-view.tsx`; it exposes local project, audit, issue, graph, and check-review surfaces through Switch IPC. The graph view includes previous/next relationship-page controls.
- Main-process coordination lives in `src/main/core/tracemind/controller.ts` and delegates to audit, project-registry, graph, issue, and verification modules.
- Project registration reuses Switch's existing local-location store; it is not a separate TraceMind project table.
- Audit records, audit evidence/report text, graph revisions/records, versioned issue records/events, and run proposals/results use Switch’s local SQLite-backed key/value store. Legacy issue records receive read-time defaults for lifecycle fields. Issue-linked graph node/event writes commit together. Check-result events carry a trusted terminal-run summary from the main process and are linked only to the issue’s associated project audit.
- Post-snapshot invalidation markers are persisted separately from the immutable audit snapshot. The marker records watcher state, a monotonic event sequence, time, bounded changed-path list/count, and truncation. The report’s advisory overlay explicitly says this does not alter fingerprints or make the scan atomic.
- `TraceMindLiveMonitor` implements a bounded, identity-checked Parcel watcher adapter. It excludes credential paths, validates event paths, caps each batch at 1,000 events and retained unique paths at 200, persists stale/error/overflow/stopped state, retries terminal-error persistence when an event write fails, and reports failures to unsubscribe. The audit UI exposes explicit Start/Stop controls; the controller requires separate native approval, binds the monitor to the audit root identity, allows one active monitor at a time, and closes active monitors on app shutdown. Monitoring is optional and not automatically started. Once approved, delivered changes save bounded local notes and schedule new audit/graph snapshots without executing project commands or calling the model. On the first report or status read after a process restart, a persisted `watching` marker with no live process-local monitor is changed to `stopped`/stale because the old watcher did not survive the process.
- A passed check proves only that the recorded approved command satisfied its execution checks. It does not prove that the check covers a reported symptom or resolves an issue.

## Project intelligence, audit, and dependency coverage

Audits use bounded descriptor-relative filesystem operations, record Git revision/dirty state where available, and store path-aware fingerprints for eligible files. The filesystem walk is limited to 50,000 entries and depth 48; the default audit fingerprint budget is 128 MiB (the service accepts an explicit maximum up to 1 GiB). The scan is not an atomic filesystem snapshot: files can change during scanning, and a Git revision does not identify all dirty content. Fingerprints cover eligible files only.

Language and manifest counts are derived from finite filename maps. The language summary recognizes many common source/config extensions (including C/C++, C#, Objective-C, Go, Java, Kotlin, Scala, JavaScript, TypeScript, Python, Rust, Ruby, PHP, Swift, Dart, and others); this recognition does **not** imply a parser, dependency resolver, or build recipe exists. The manifest list includes common npm, Python, Java/Gradle, Go, Rust, .NET, Ruby, PHP, Swift, Dart, Deno/Bun, and other ecosystem files; detection is not equivalent to parsing.

The dependency inventory is local/offline and has the following concrete closure support:

| Evidence | Supported parsing                                                                                                                                                        | Important limits                                                                                                                                        |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| npm      | `package-lock.json` and `npm-shrinkwrap.json`, lockfile versions 2 and 3; root dependencies, dev/optional/peer dependencies, and deterministic package dependency edges. | Workspace links are not recursively joined. Missing or ambiguous resolutions, unsupported versions/names, and truncated evidence make coverage partial. |
| pnpm     | `pnpm-lock.yaml`, lockfile versions 6 through 9; package/snapshot dependency edges.                                                                                      | Unsupported package key/source forms or ambiguous resolutions are omitted and reported.                                                                 |
| Cargo    | `Cargo.lock`, versions 1 through 4; package edges and direct links from a same-directory `Cargo.toml`.                                                                   | Cargo workspace member manifests are not joined, so direct member linkage can be incomplete.                                                            |
| Poetry   | `poetry.lock`, metadata lock versions 1.1, 2.0, and 2.1; package edges and direct links from a same-directory `pyproject.toml`.                                          | Ambiguous duplicate package versions and unsupported lock versions are reported as partial.                                                             |

`package.json`, `Cargo.toml`, and `pyproject.toml` can provide direct-only declarations without a matching supported lockfile. These direct-only rows do not establish transitive closure. Yarn, uv/Pipfile/requirements, Go, Maven/Gradle, Composer, Ruby, Bun/Deno, Swift, NuGet, Dart, and other detected files do not receive dependency closure parsing in this inventory today; unsupported or unparsed metadata remains visible as a limitation. No package manager, registry, URL, or network is used to resolve packages.

Capture and persistence bounds include a 1 MiB manifest, 8 MiB lockfile, 16 MiB aggregate dependency content, 128 captured dependency-evidence files, 10,000 packages, and 20,000 edges. A partial filesystem walk also makes dependency status partial even when each parsed lockfile was individually supported; aggregate omitted lockfile/unsupported-file counts survive path-list truncation. The general graph parser accepts up to 16 MiB per supported source file; files beyond that limit can still receive path/fingerprint evidence when the audit budget permits, but their source relationships remain an explicit omission. Oversized, unreadable, changed, malformed, unsupported, or un-fingerprintable files can make coverage partial; they do not establish that corresponding code or dependencies are absent.

Audit comparison compares compatible persisted snapshots and requires another audit to capture later content. A user can separately start the optional monitor after approval; its invalidation marker supplements the snapshot and marks freshness stale after a change, watcher error, overflow, stop, or process restart. A separate single-flight refresh queue captures new audits and graph revisions after delivered change batches; it never mutates old fingerprints. “No change recorded so far” is not proof of complete filesystem freshness. A new audit, manual or produced by the approved refresh queue, is required to establish a new snapshot.

## Graph coverage and limits

The graph parser uses the TypeScript syntax tree for `.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, and `.cjs`. Bounded lexical/token adapters cover C, C++, C#, Go, Java, Python, and Rust source extensions. Rust nested `use` groups expand to original import paths with aliases preserved as target identity; malformed/deep/unsupported trees fail explicitly. C/C++ macro definition bodies are skipped as preprocessing syntax; known macro calls are retained only as ambiguous references, not extracted definitions. The graph adapter for `package.json` captures direct dependencies/devDependencies/peerDependencies/optionalDependencies; the separate audit dependency inventory has the four lockfile closure adapters above. Other languages may appear in filename inventory but have no source parser here.

Each graph node/edge retains revision, source/provenance, extraction method, and certainty (`direct`, `heuristic`, or `ambiguous`). Relationship pages are keyset-paginated, scoped to one project and revision, capped at 50 relationships per page, and capped at 128 KiB for each stored relationship payload. A graph revision supports at most 100,000 nodes and 400,000 relationships. Pagination enables consumers to enumerate persisted edges within those caps; it does not repair parser omissions or convert heuristics into a complete architecture map.

Neighborhood inspection remains a different operation. It enforces maximum depth 64, 1,000 returned nodes, 100,000 examined edges, 10 seconds, and a caller-specified bounded memory budget. The renderer requests a smaller neighborhood. `CALLS` edges are name-based extraction/resolution; `TESTS` edges are inferred from test declarations and extracted calls. Same-named functions, dynamic dispatch, generated code, runtime behavior, and language-specific semantics are not fully resolved. A test edge is not proof that a test executes or covers a function.

## Issue workflow and report boundary

The issue record supports `open`, `investigating`, and `resolved`; allowed transitions and resolution rationale are enforced in persistence. A distinct investigation phase runs from `reported` through evidence gathering, hypotheses, planned/approved/executed checks, evaluation, finding, verification, or terminal inconclusive outcomes. Legal phase transitions are versioned in the same database transaction as the append-only issue timeline. The renderer selects only canonical legal next phases, and the main-process endpoint requires the issue's same-audit recorded check event when a check outcome is attached. Priority and owner are versioned edits. Timeline events are append-only, project-scoped, and bounded to 100 events / 4 MiB total serialized events per issue. Manual entries can be labeled observations, hypotheses/inferences, findings, or evidence. An issue-linked graph observation stores the graph node and event in one transaction; command-like graph notes remain graph entries and are not mislabeled as executed checks. Evidence can be marked stale on revision change and explicitly reviewed against the latest stored graph revision with rationale. There is no automatic reopen trigger or proof that evidence covers a reported symptom.

The separate investigation report reflects the issue, current investigation phase and phase history, timeline, current graph revision, linked graph-node source/provenance, structured terminal check outcomes, and linked-audit freshness marker when one exists. Phase history and issue events survive database reopen. Only completed/refused runner records from the issue’s linked audit can create check-result events; the report shows recorded status, verification flag, exit/signal, and effective process/memory limits. It distinguishes `unmonitored`/unknown freshness from an unchanged active marker and stale/error/overflow states. User-supplied notes remain notes, not runner output. Coverage is **partial**: not every event has source location, graph/report reads are not an immutable cross-store transaction, old historical events can be stale, and unrecorded behavior/evidence is outside the report. A check result never transitions an issue or proves symptom coverage.

## Check discovery and platform controls

Discovery reads a bounded set of fingerprint-matched manifests from the audited snapshot and proposes fixed recipes only: npm/pnpm/yarn/bun `test` scripts, Python `pytest` or `unittest discover`, `go test ./...`, offline/locked `cargo test`, offline Maven `test`, and offline Gradle `test`. Discovery does not execute manifest contents. Package scripts remain untrusted project-controlled code; the user receives a proposal and grants a one-use approval. Approval is an authorization step, not a containment boundary.

| Host    | Current status                                | Evidence and caveat                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| macOS   | **Available, unverified only**                | On this host the controller permits an explicitly approved check only when Seatbelt is present. `ProcessAdapter` records memory/process controls as false; successful process exit does not imply complete capture or descendant cleanup, so persisted outcomes remain unverified. The ordinary fixture integration executed npm test and Python unittest sequentially on this Mac. A hard-capped, verified mode still requires a separately designed native supervisor. |
| Linux   | **Partial / capability-dependent**            | The runner requires Bubblewrap and a private cgroup v2 below a writable delegated ancestor with `memory` and `pids` already enabled. It never enables controllers on a shared parent. Missing capability fails closed; cleanup uncertainty prevents a verified result.                                                                                                                                                                                                   |
| Windows | **Unavailable in production controller path** | `checkRuntime()` only enables Darwin/Linux. Windows approved-root handoff and MXC ProcessContainer request builders are tested helpers, but are not wired to controller execution or an installed production runner.                                                                                                                                                                                                                                                     |

Across platforms, a command is only marked verified when execution matches the approved proposal, isolation and effective limits are confirmed, output is complete, the exit is successful, and process termination is confirmed. macOS execution deliberately fails these verification predicates when resource limits or descendant cleanup are unconfirmed. A detached descendant or uncertain cleanup cannot be reported as a verified check. A verified check still does not prove issue resolution.

## Local-first, security, and interpretation

- Core audit, graph, issue/report, and run stores use Switch’s local SQLite-backed key/value table. The legacy local-first verifier predates the optional model gateway and runtime receiver and now reports them; it is not a current network-free certification; this does not prove the entire desktop app or user-launched commands are network-free.
- Project selection and consent are separate. Audit/check grants are purpose/root scoped and one-use in memory, but consent alone is not an OS security boundary and is not a persisted approval.
- Repository files, manifests, package scripts, paths, and captured output are untrusted. Check proposals remain constrained and require explicit approval.
- Filesystem exclusions reduce exposure but do not detect every secret. Reports and graph output retain omission and truncation notices.
- Cancellation requests termination; it is not universal proof that every descendant exited. Process cleanup uncertainty prevents verification.
- The graph is evidence with provenance and extraction-method limits, not a runtime call graph or proof of causation.
- A central configurable brain gateway and local runtime ingestion are present. Project sharing is default-deny and root/provider-bound; only approved metadata and optionally selected notes leave the device. Local session IPC supplies context before addressed messages and an agent report tool requests minimal Switch alerts. A saved provider is not proof of a working model connection; live platform ingress and final delivery remain unverified. Provider-egress controls, prompt-injection handling, citation validation and runtime correlation remain bounded defenses, not a complete hallucination or independent-agent sandbox solution.

## Roadmap

1. **P0 — macOS verified checks:** implement a supported native per-run memory/process-tree supervisor and confirmed descendant cleanup before promoting the current approved Seatbelt execution path from unverified to verified. The working path is tested natively on this Mac; no VM is required for the current unverified mode.
2. **P0 — product truth:** keep the six-category status matrix synchronized with source, focused tests, and the user-facing report; do not describe the overall workflow as complete.
3. **P1 — live monitor hardening:** validate watcher lifecycle across app restart, root replacement, overflow/error recovery, new-audit refresh, and supported packaged filesystems. Keep monitoring optional/explicit and freshness advisory; it does not establish atomic snapshot semantics.
4. **P1 — investigation report:** add durable export, broader source references, and a consistent snapshot across issue, graph, audit, and run stores while retaining the partial-coverage contract.
5. **P1 — platform completion:** validate installed macOS workflow and accessibility after the containment backend is implemented. Treat Windows controller integration and packaged-app evidence as a separate later milestone. Retain Linux’s capability-dependent status.
6. **P2 — evidence quality:** version parser/exclusion policy, expand dependency and source parser coverage incrementally, and mark ambiguous relationships uncertain. Keep unsupported extensions and incomplete coverage visible.
7. **Next — deployed brain/bridge validation:** validate the chosen provider and installed communication connector end to end, then evaluate hallucinations and stronger independent-agent filesystem enforcement. Keep conclusions advisory and preserve explicit sharing controls.
